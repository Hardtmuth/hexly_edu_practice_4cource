# Модульное тестирование (Unit Testing) и аудит безопасности

### Задание
Перед передачей подсистемы заказчику необходимо гарантировать, что математический метод расчета материалов работает безотказно во всех крайних случаях, а интерфейс защищен от критических ошибок ввода.
 
**Задача**:
  1. **Написание Unit-тестов**: Создайте отдельный тестовый модуль (используя `unittest`/`pytest` для `Python`, `JUnit` для `Java` или `NUnit` для `C#`). Напишите **не менее 5** тест-кейсов для метода расчета материалов из Подзадания 2:
    - Тест 1 (*Стандартный*): Проверка обычного корректного расчета с известным результатом.
    - Тест 2 (*Округление*): Проверка, что дробный результат округляется строго в большую сторону (вверх) до целого числа.
    - Тест 3 (*Несуществующий тип*): Проверка возврата -1 при передаче некорректных ID типов продукции/материала.
    - Тест 4 (*Отрицательные параметры*): Проверка возврата -1 при передаче отрицательных размеров (`param_1` или `param_2`).
    - Тест 5 (*Нулевое количество*): Проверка возврата -1, если количество продукции равно нулю или меньше.
  2. **Аудит безопасности (Защита от SQL-инъекций)**: Проверьте код текстовых полей поиска или авторизации (если применимо) и окон добавления партнера. Убедитесь, что все SQL-запросы используют **параметризованные аргументы** (экранирование), а не прямую конкатенацию строк (например, `execute("... WHERE id = %s", (user_id,))` вместо `execute(f"... WHERE id = {user_id}")`).
  3. **Формирование отчетного лога**: Добавьте в приложение простейшее логирование ошибок (в файл `app.log` или в консоль). При возникновении исключений (`try...except`) в файл должна записываться дата, время и понятный текст ошибки.
